MERIDIANPRIVACY POLICY

Privacy Policy

LAST UPDATED · 05 OCT 2026 · APPLIES TO drewosi.github.io/lucid-engine

The short version: Meridian runs in your browser. We operate no servers, so we cannot see your files, your questions, your AI conversations or your API key. The only personal data that can reach us is an email you choose to send us. Everything else stays on your machine, travels directly between your browser and the AI provider you chose under your own account, or goes wherever you send a share link. The workbench's usage log is opt-in, off by default, and stays in your browser unless you point it at a collector of your own.

§01Who we are

This site and the Meridian workbench are operated by Drew Osipenko ("we", "us"). Contact for anything in this policy, including privacy requests: drewosipenko@gmail.com.

§02What we never receive

Meridian is a static site with no backend: no database, no account system and no server-side logging of your activity by us. We never receive:

  • the project files you load into the workbench, which your browser reads into the tab's memory only;
  • your questions and the AI's answers;
  • your API key.

The architecture enforces this, and you can verify it in the public source code or in your browser's network inspector.

§03Data stored in your browser (localStorage)

Meridian keeps a small amount of data in your browser's localStorage so the pages work. This data stays on your device unless noted below, and you can delete all of it at any time.

The workbench settings panel includes a single button that removes every Meridian key from your browser, including any entry left in localStorage by an earlier version of the site. Loaded project files and conversation history are held in memory only and are gone when the tab closes.

If you save a project or a multi-repo workspace, its record is kept in your browser's IndexedDB: the name you give it, repo names, file and token counts, the list of files you unticked, your ignore patterns and context settings, and, in Chromium browsers, a folder handle that the browser asks your permission to reuse. Never file contents: reloading a saved workspace asks you to pick each folder again. Delete a saved entry with its ✕, or everything with the clear-all button.

If you turn on the optional usage log (§07), its events are also kept in your browser's IndexedDB, in a separate database. It is off by default and holds nothing until you turn it on.

§04Data sent to your AI provider

When you use the workbench with a model connected, your browser sends your question, the project context for it, and your API key directly to the provider you chose: Anthropic (api.anthropic.com), OpenAI (api.openai.com), or a custom endpoint you configure. That processing happens under your own account with that provider and under that provider's terms. We are not a party to it, do not sit in the middle of it, and cannot access it. In LOCAL mode, nothing is sent at all.

Review your provider's privacy documentation, for example the Anthropic Privacy Policy or the OpenAI Privacy Policy. Each request carries:

  • the files you tick in the context panel. In FULL mode they go whole. In SMART mode the workbench sends the most relevant of them, some as line-numbered excerpts, plus a project map of the ticked files: their paths, size estimates and the first lines of a few key files;
  • while GROUND is on (the default), short line-numbered excerpts that the workbench's local search found for that question, which can come from any file you loaded, ticked or not;
  • the lines of any evidence you pin;
  • the earlier questions and answers of the conversation, which go with every new question;
  • in a multi-repo workspace, the names of the loaded repos.

[ PREVIEW SEND ] shows the exact context before anything goes. To keep a file out entirely, don't load it (or exclude it with an ignore pattern), or turn GROUND off and untick it.

§05Share links and bundles

The workbench can share a loaded project in two ways, both without any server:

  • A share link. Your browser compresses the files you tick (their paths, full text and last-modified times) plus a project name, and for a multi-repo workspace the repo names, into the link itself, in the part after #. Browsers never send that part of an address in a request, so GitHub Pages never receives it, and neither do we.
  • A bundle (a .meridian file). The same data as readable JSON, for projects too big for a link. It goes wherever you send it.

A link or bundle is the code itself. Anyone who has it can read those files. So can any service it passes through: the chat app or email provider you paste it into stores the message, link included, and the address can stay in the browser history of whoever opens it. There is no server, so there is nothing we can revoke or expire: once sent, it works for as long as someone keeps it. Treat it like sending the files.

Never included: API keys, provider settings, conversations, saved projects, or anything else Meridian keeps in your browser's storage. Files that look like secrets (.env files, private keys, credential files) start unticked, but you choose what goes in.

When someone opens a link or bundle, it is unpacked in their browser tab and held in memory only. It opens read-only, nothing about it is written to their browser's storage, and the # part is removed from the address bar once it has loaded.

§06Email contact (the only data we can receive)

The site has no forms. The only way personal data can reach us is if you email drewosipenko@gmail.com. If you do, we receive your address and whatever you write, use them only to reply to you, and delete them on request. No newsletters, no resale, no ad pixels.

§07Cookies and analytics

We set no cookies. There are no advertising trackers, no social pixels, no fingerprinting.

We run no analytics on this site and receive no usage data. If that ever changes, this policy will say so first. The site is hosted on GitHub Pages; GitHub may log standard web-server data (such as IP addresses) to operate the service (see the GitHub Privacy Statement). The workbench page loads no third-party assets or scripts at all: every request it makes goes to GitHub Pages (the page itself), directly to your chosen model provider under your own key when you ask a question, or, only if you set one up yourself, to your own analytics endpoint (below).

Opt-in usage log (workbench). The workbench can keep a log of how you use it, for you. It is off by default, and while it is off nothing is recorded. When you turn it on in Settings, each event is stored in your browser's IndexedDB and nowhere else:

  • Stored: the time, the kind of question (for example "definition" or "import cycles"), the provider, whether the LOCAL engine or a model answered, how long the answer took, token counts if the provider reported them, how many repos were loaded and the question scope, the number of loaded files, and when you created a share link, saved a share bundle or added a repo.
  • Never stored: code or file contents, file paths, or API keys.
  • Question text is stored only if you also turn on a second switch, "Also store question text", which is off by default. It is cut to 300 characters, and anything that looks like a key is removed.
  • Export and delete: the usage-log panel exports everything as JSON or CSV and has a "Clear all data" button. The settings clear-all button deletes the log as well.

Your own endpoint (optional). Settings has a URL field for people who run their own collector. It is blank by default. Only when you fill it in and the usage log is on does the workbench send the same events (question text only if you store it) to that URL. That is the only network request the usage log ever makes, and it goes to a server you chose, never to us: there is no collection server of ours in the code. Events from LOCAL mode are never sent. On the hosted site this page's security policy only allows a collector on your own machine (localhost). Whoever runs that endpoint is responsible for what happens to the data there.
